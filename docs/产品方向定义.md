## 一、产品定位

### 1.1 一句话定位

**PulseCast（怦然）是一款免费、本地优先的主播心率直播伴侣，让任何主播用蓝牙手环/手表就能在直播画面中展示实时心率，并通过心跳触发互动效果。**

### 1.2 核心问题

国内主播想在直播中展示心率，目前面临的困境是：

- **没有好用的国产方案。** 现有工具要么是英文产品（HypeRate、HeartCast），要么需要翻墙下载，要么是零散的技术博客教程（需要自己装 Python、加载 Chrome 扩展），对普通主播极不友好。
- **现有方案功能单一。** obs.cn 的心率插件只能显示数字，没有视觉效果、没有互动玩法。HypeRate 功能丰富但依赖云端、以 Twitch 生态为中心，不适配国内直播平台。
- **隐私顾虑。** 云端方案意味着心率数据上传到第三方服务器，部分主播和观众对此敏感。

### 1.3 价值主张

| 维度 | PulseCast 的回答 |
|------|-----------------|
| 为谁？ | 国内游戏/娱乐/健身主播，以及 VRChat 玩家 |
| 解决什么？ | 让心率成为直播间的"第二画面"——不只是数字，而是有视觉冲击力和互动玩法的直播元素 |
| 怎么解决？ | 蓝牙直连 + 本地服务器 + OBS 原生插件（GPU 加速特效）+ 手机遥控 |
| 凭什么不同？ | ① 完全本地，零云端，心率数据不出电脑 ② OBS 原生 C 插件提供心跳抖动/发光等 GPU 特效，浏览器叠加做不到 ③ 阈值引擎支持心率触发场景切换/警报 ④ 中文优先，适配小米/华为手环 ⑤ 完全免费开源 |

### 1.4 商业模式

**当前阶段：完全免费 + 开源。**

远期规划：PulseCast 作为未来"直播辅助工具套件"的心率模块，套件整体考虑商业化。心率模块本身保持免费，作为套件的引流入口和差异化卖点。

### 1.5 成功指标

| 阶段 | 指标 | 目标 |

| v0.9 发布后 1 个月 | GitHub Star 数 | 500+ |

## 二、目标用户

### 2.1 核心用户画像

**画像 A：游戏主播（主力用户）**

- 年龄 18-30，在 B站/抖音/斗鱼/虎牙直播
- 玩恐怖游戏、竞技游戏、挑战类内容
- 想让直播更有"节目效果"——心率飙升 = 名场面
- 技术水平中等，会装 OBS 但不想折腾命令行
- 设备：小米手环 / 华为手环（国内最普及）

**画像 B：健身/运动主播**

- 在直播健身、跑步、骑行
- 需要展示心率来证明训练强度，增加专业感和信任感
- 设备：运动手表（华为 GT 系列、Polar 心率带）

**画像 C：VRChat 玩家**

- 在 VRChat 中社交/直播
- 想让虚拟形象随心跳做出反应（发光、抖动、表情变化）
- 设备：Apple Watch / 蓝牙心率带

### 2.2 用户分层

| 层级 | 定义 | 策略 |
|------|------|------|
| 种子用户（v0.9） | 首批 50-100 名，从 B站/即刻/V2EX 招募 | 1v1 支持，收集反馈，协助制作教程 |
| 早期用户（v1.0） | 发布后 1-3 个月的活跃用户 | 引导产出教程视频，建立 QQ 群/微信群 |
| 大众用户（v1.x） | 口碑传播后的自然增长用户 | 优化首次使用体验，降低上手门槛 |

## 三、竞品分析与差异化

### 3.1 竞品格局

| 产品 | 类型 | 价格 | 平台 | 核心优势 | 核心短板 |
|------|------|------|------|---------|---------|
| **HypeRate.io** | 云端 SaaS | 免费 | Web + 多平台 | 功能最全（100+皮肤、ECG、GPS、情绪剪辑）；支持 Twitch/YouTube/TikTok | 依赖云端；Twitch 生态中心；国内访问不稳定；无中文 |
| **HeartCast** | iOS App | 免费 | Apple Watch + iOS | Apple 生态体验好 | 仅限 Apple；功能单一 |
| **PulseOverlay** | 开源工具 | 免费(MIT) | Python + Chrome 扩展 | 本地优先；开源 | 无正式发布版；需装 Python + 手动加载扩展；功能基础 |
| **obs.cn 心率插件** | OBS 插件 | 未知 | OBS (Windows) | 支持小米/华为手环；中文 | 仅显示数字；无视觉效果；无互动；仅 Windows |
| **散落的博客教程** | DIY 方案 | 免费 | 各种 | 能跑就行 | 门槛极高；无维护；无统一体验 |

### 3.2 PulseCast 的差异化壁垒

1. **OBS 原生 C 插件 = 视觉壁垒。** 浏览器叠加（Browser Source）受限于 CSS 动画，而 PulseCast 的原生插件直接调用 GPU shader，实现心跳发光（GLSL 5×5 邻域辉光）、镜头抖动等效果。这是 HypeRate 和所有浏览器方案做不到的。

2. **本地优先 = 信任壁垒。** 心率是敏感生理数据。"数据不出电脑"是对云端方案的结构性优势，尤其在国内用户对隐私日益敏感的环境下。

3. **阈值引擎 = 玩法壁垒。** 心率超过阈值 → 自动切换 OBS 场景 / 触发闪光 / 触发抖动。这为"心率挑战"类直播内容提供了基础设施。

4. **中文优先 + 国产设备适配 = 渠道壁垒。** 小米手环、华为手环是国内主播最常用的设备。做好这些设备的首次连接体验，就是最大的获客优势。

## 四、产品形态与平台策略

### 4.1 产品形态

PulseCast 是一个**本地服务 + 多前端**的架构：

```
┌─────────────────────────────────────────────────┐
│           PulseCast Server (Rust)                │
│   BLE连接 ← 阈值引擎 → WebSocket广播 → OSC输出  │
│              端口 :4567                          │
└──────┬──────┬──────┬──────┬──────┬───────────────┘
       │      │      │      │      │
   ┌───┴──┐┌──┴──┐┌──┴──┐┌──┴──┐┌──┴───┐
   │Tauri ││ OBS ││ OBS ││手机 ││VRChat│
   │桌面端││浏览器││原生 ││遥控器││ OSC │
   │(设置)││叠加 ││插件 ││(PWA)││      │
   └──────┘└─────┘└─────┘└─────┘└──────┘
```

### 4.2 平台优先级

| 优先级 | 平台 | 理由 | 当前状态 |
|--------|------|------|---------|
| **P0** | OBS 浏览器叠加 | 最低门槛，所有 OBS 用户 30 秒内可用 | ✅ 已实现，需修 token 问题 |
| **P0** | OBS 原生插件 | 核心差异化（GPU 特效），技术壁垒 | ✅ 已实现，需修 WS 路径 |
| **P0** | Tauri 桌面端 (Mac + Windows) | 设置界面 + 服务器托管 + 首次使用引导 | ✅ 已实现，需完善 FTUE |
| **P1** | 手机遥控器 (PWA) | 直播中远程调阈值/切场景，实用性强 | ✅ 已实现，需修 token |
| **P2** | iOS/Android 原生 App | 移动端独立使用（手机直播场景） | ⚠️ Tauri Mobile 配置存在，未验证 |
| **P3** | 直播伴侣套件集成 | 远期，作为更大产品的一部分 | ❌ 未启动 |

### 4.3 关键决策：不做云端

PulseCast 坚持本地优先架构。不引入云端账号系统、不上传心率数据、不做云端同步。这是产品定位的核心约束，不是技术限制。

## 八、技术约束与原则

### 8.1 不可违背的约束

1. **本地优先。** 不引入云端依赖。所有数据在本机处理。
2. **免费开源。** 代码在 GitHub 公开，MIT 或同等许可证。
3. **OBS 兼容。** 核心体验围绕 OBS 构建，不假设用户使用特定直播平台。
4. **蓝牙直连。** 不依赖手机 App 中转（手机遥控器是可选增强，不是必须路径）。

### 8.2 技术栈确认

| 层 | 选型 | 理由 |
|----|------|------|
| 后端 | Rust (axum + tokio + btleplug) | 性能、安全、单二进制分发 |
| 桌面壳 | Tauri v2 | 轻量、跨平台、Rust 原生集成 |
| 前端 | 原生 HTML/CSS/JS | 零依赖、OBS 浏览器源兼容、加载快 |
| OBS 插件 | C (libobs) | 原生性能、GPU shader 访问 |
| 移动端 | PWA（短期）→ Tauri Mobile（中期） | 快速验证 → 原生体验 |
| CI/CD | GitHub Actions | 已有，macOS dmg + Windows exe |

### 8.3 已知技术债（v0.9 后处理）

| 问题 | 影响 | 优先级 |
|------|------|--------|
| 前端无构建工具/类型检查 | 维护困难，逻辑重复 | P2（v1.0 考虑迁移） |
| OBS 插件 JSON 解析用 strstr | 特殊字符可能崩溃 | P2 |
| token 用 DefaultHasher 生成 | 非密码学安全 | P3（本地场景风险低） |
| CSP 为 null | 安全基线缺失 | P2 |
| 无集成测试 | 回归风险 | P2 |

## 九、增长策略（概要）

### 9.1 冷启动渠道（v0.9 发布前后）

| 渠道 | 优先级 | 策略 |
|------|--------|------|
| B站 | ★★★★★ | 制作"5分钟在直播里显示心率"教程视频；联系恐怖游戏/挑战类主播试用 |
| 即刻 | ★★★★☆ | Build in Public 系列，分享开发过程 |
| GitHub | ★★★★☆ | README 做好中英文说明，Awesome 列表投稿 |
| V2EX / 少数派 | ★★★☆☆ | 发布帖 + 技术分享 |
| QQ群/微信群 | ★★★☆☆ | 建立用户社群，收集反馈 |

### 9.2 内容策略

核心内容方向：**"心率让直播更好看"** — 不是技术教程，而是展示效果。

- 恐怖游戏主播心率飙升名场面剪辑
- "心率超过 150 就切换惩罚场景"挑战
- VRChat 虚拟形象随心跳发光
- 健身主播用数据证明训练强度

### 9.3 关键原则

- **不贪多。** 先打透 B站 + 即刻两个渠道。
- **效果驱动。** 所有内容先展示"看起来有多酷"，再教"怎么设置"。
- **社区共建。** 鼓励用户分享自己的叠加样式和玩法。

## 十、风险与应对

| 风险 | 可能性 | 影响 | 应对 |
|------|--------|------|------|
| 小米/华为手环 BLE 兼容性问题 | 高 | 核心用户无法使用 | 种子用户阶段重点测试 Top 5 设备；建立设备兼容性列表 |
| OBS 版本碎片化 | 中 | 原生插件在某些版本崩溃 | CI 矩阵测试 OBS 28/29/30；浏览器叠加作为兜底 |
| 一人开发资源瓶颈 | 高 | 迭代速度慢 | 严格控制 MVP 范围；优先修 Bug 而非加功能 |
| Apple Watch 连接问题 | 中 | iOS 用户流失 | v0.9 不承诺 Apple Watch 支持；文档说明替代方案 |
| 竞品跟进（HypeRate 出中文版） | 低 | 差异化缩小 | 本地优先 + OBS 原生插件是结构性优势，不易复制 |

| 编号 | 决策 | 理由 |
