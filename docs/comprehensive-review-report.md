## 一、项目现状一句话总结

**PulseCast 核心安全与基础设施已加固（WS token + CI/CD + 设置持久化），技术健康度从 6.5 提升至 7.5/10；当前瓶颈已从"安全裸奔"转移至"体验打磨"——FTUE 引导断裂、API 层认证残留缺口、移动端 token 适配未完成，距离可公开发布约需 2-3 周集中打磨。**

## 二、Top 5 关键问题（跨技术/产品/增长）

> v1.1 更新：原 #1（WS 无认证）已修复、#3（无 CI/CD）已修复、#4（设置不持久化）已修复。以下为重验后重新排序。

| 排名 | 问题 | 维度 | 影响 | 状态 |
|:---:|------|------|------|------|
| 1 | **OBS 配置引导缺失 + FTUE 断裂** | 产品×增长 | 用户从"连接设备"到"OBS 出画面"存在 3 个断点，预计激活率 <20%；直接杀死冷启动转化 | 未修复 |
| 2 | **HTTP API 层缺 token 校验（Origin guard 可绕过）** | 技术×安全 | 同机 curl/native 进程无 Origin 头即可调用 /api/source、/api/config，控制直播画面或篡改配置 | 新发现 |
| 3 | **mobile.js 未适配 token 认证** | 技术×产品 | Tauri 桌面模式下移动端 WS 连接被拒，"手机遥控器"卖点当前不可用 | 新发现 |
| 4 | **OBS 插件 WS 路径不匹配（"/" vs "/ws"）** | 技术×产品 | OBS 插件连接新版服务端时可能握手失败，核心功能链路断裂 | 新发现 |
| 5 | **Tauri mobile 为 beta + 移动端方案不确定** | 技术×产品 | 移动端无法稳定发布，中长期移动端路线缺乏确定性 | 未修复 |

**已修复（从 Top 5 移除）：**
- ~~WS 无认证~~ → 已实现 token 认证（Tauri IPC 下发 + WS ?token= 校验）
- ~~无 CI/CD~~ → 已建立 GitHub Actions（test + clippy + build + release）
- ~~设置不持久化~~ → 已实现 config.rs + /api/config 端点

## 三、三个方向的交叉分析

### 3.1 技术债 → 推广节奏

| 技术债 | 对推广的阻塞 | 状态 |
|--------|------------|------|
| ~~WS 无认证~~ | ~~无法安全公开发布~~ | ✅ 已修复 |
| ~~无 CI/CD~~ | ~~无法支撑快速修 Bug 节奏~~ | ✅ 已修复 |
| ~~OBS glow filter 硬编码 1080p~~ | ~~4K 主播看到效果异常~~ | ✅ 已修复 |
| HTTP API 缺 token（Origin guard 可绕过） | 同机恶意进程仍可控制直播；安全叙事不完整 | ⚠️ 待修（~2h） |
| OBS 插件 WS 路径 "/" vs "/ws" | 插件连不上新版服务端 → 核心演示链路断裂 | ⚠️ 待修（~1h） |
| mobile.js 未适配 token | "手机遥控器"演示不可用 → 推广视频少一个卖点 | ⚠️ 待修（~2h） |
| 前端无框架 | 推广期间若需紧急改 UI，改动成本高、回归风险大 | 暂不阻塞发布 |

**结论：原 P0 阻塞项（安全+CI）已清除。剩余 3 个技术缺口（API token、OBS 路径、mobile token）总计约 5h 工作量，是发布前的硬性前置条件。**

### 3.2 产品缺口 → 获客转化

| 产品缺口 | 对获客的影响 | 状态 |
|----------|------------|------|
| FTUE 断裂（OBS 配置无引导） | 推广视频吸引下载后，用户 5 分钟内无法出画面 → 卸载 | 未修复 |
| ~~设置不持久化~~ | ~~第二次使用体验骤降~~ | ✅ 已修复 |
| mobile.js 未适配 token | "手机遥控器"功能当前不可用 → 产品完整度感知下降 | 新发现 |
| 无 Apple Watch 支持 | 健身主播（P1 目标用户）核心设备无法连接 → 该细分市场无法切入 | 中期规划 |
| 移动端方案不确定 | 中长期移动端路线缺乏确定性 | 未修复 |

**结论：FTUE 仍是获客转化的第一瓶颈。设置持久化已修复（利好留存），但 mobile token 适配需尽快补上以兑现"手机遥控器"卖点。**

### 3.3 推广策略 → 产品/技术反馈

| 推广需求 | 对产品/技术的要求 | 状态 |
|----------|-----------------|------|
| B站演示视频需要"3 分钟出效果" | FTUE 必须做到 3 步内完成配置 | 待做 |
| OBS 插件市场提交 | 需要 Windows + macOS 双平台稳定构建（CI/CD） | ✅ 已就绪 |
| 开源社区贡献者引入 | 需要 CONTRIBUTING.md + 可运行的测试套件 | ✅ 已就绪 |
| OBS 插件演示链路 | 插件 WS 路径需与服务端一致（"/" → "/ws"） | ⚠️ 待修 |
| "本地无延迟"核心卖点 | 需实测数据支撑（<100ms），当前架构满足但无基准测试 | 待做 |

## 五、战略建议：继续投入

**结论：继续投入，收窄发布范围，3 周内完成 v0.9.0 公开发布（原计划 4 周，因 Week 1 已完成而提前）。**

### 理由

| 维度 | 判断 |
|------|------|
| 市场真实性 | ✅ 心率直播是已验证需求（Pulsoid 有付费用户、B站相关视频播放量可观） |
| 差异化壁垒 | ✅ OBS 原生 C 插件 + VRChat OSC + 本地零延迟，三者组合目前无竞品覆盖 |
| 技术完成度 | ✅ 核心链路已跑通 + 安全加固 + CI/CD + 持久化已落地（技术健康度 7.5/10） |
| 投入产出比 | ✅ 距可发布状态仅需 2-3 周（~90h），远低于重新做一个项目的成本 |
| 一人公司适配性 | ✅ 开源 + 工具型产品，无需客服/运营团队，社区自驱动增长 |
| 变现路径 | ⚠️ 短期不变现，中期通过 Pro 订阅（多设备/高级主题/数据回放）验证 |

### 风险与对冲

| 风险 | 对冲策略 |
|------|---------|
| 发布后无人问津 | 发布前已有种子用户验证；首月聚焦 P0 渠道（B站/OBS 论坛），不撒网 |
| 技术债导致频繁崩溃 | ✅ 风险已降低：CI 兜底 + 安全加固已落地；发布版仅含已验证功能 |
| 竞品跟进 | 开源 + 社区粘性是护城河；保持 2 周一次迭代节奏 |
| 精力分散 | 30 天内只推 PulseCast 一个项目，不启动新项目 |
| OBS 插件兼容性 | Week 1 修复 WS 路径 + 种子用户阶段覆盖 OBS 30/31 版本测试 |
